# Файлы прогона

У каждого участника свой каталог `runs/<эксперимент>/<участник>/`. Замороженный конфиг (`config.json` и `config.sha256`) один раз пишет при старте эксперимента модуль `traider/config.py`, он же его читает. Всё остальное в каталоге читает и пишет только модуль `RunStore`; брокеры, сессия и отчёт ходят в файлы через него. Журнал заявок это запись, которая должна пережить сбой.

| Файл | Что в нём |
|---|---|
| `config.json` | Замороженный конфиг участника: модель, брокер, лимиты, вселенная, панель, цены токенов (и модели аналитика, если он есть), критерии и тексты промптов |
| `config.sha256` | SHA-256 байтов `config.json`; не сошлась или файла нет: прогон помечается как изменённый |
| `orders.jsonl` | Журнал заявок, только дописывается. Строка на событие; поля перечислены ниже |
| `forecasts.jsonl` | Прогнозы: день, тикер, вероятность |
| `state.json` | Состояние прогона; ключи перечислены ниже |
| `sessions/<день>.json` | Запись сессии дня; поля ниже |
| `prices/<день>.json` | Снимок цен дня: тикер и цена, только годные котировки |
| `ticks.jsonl` | Строка на каждый тик, который дошёл до прогона, ошибки тоже; поля ниже |

## Ключи `state.json`

Сверено с кодом на 2026-11-15.

- `status`: статус прогона (значения ниже).
- `notes`: заметки агента, до 2000 знаков.
- `started_with`: режим и брокер, записанные при старте, вне `config.json`; их сверяет тик, а `start` и тик по ним находят прогоны на одном счёте Alpaca.
- `first_day`: день первого тика; с него считаются пропущенные дни.
- `last_sync`: время последней сверки с брокером.
- `stops`: желаемый стоп каждой удерживаемой бумаги (у счёта Alpaca; бумага без него значит, что счёт не только наш).
- `entries`: последняя известная цена входа каждой бумаги (Alpaca после продажи её не отдаёт).
- `seen_qty`: последнее известное количество каждой бумаги (для доли восстановленного закрытия).
- `account`: сохранённый счёт: деньги, позиции, пик капитала.
- `run_uid`: случайный код прогона в id заявок у брокера; пишется при первом обращении к брокеру после проверки счёта.
- `broker_since`: время первого обращения к брокеру; с него начинается первое окно сверки.
- `order_seq`: счётчик id заявок стопов.
- `finish_day`: день последней сессии; через 5 торговых дней после него прогон `finished`.
- `died_on`: день гибели.

## Поля события журнала заявок

- У всех: `seq`, `ts` (по умолчанию часы машины; брокеры передают время рынка), `day`, `kind`, `symbol`, `notional`, `qty`, `price`, `stop_price`, `thesis`, `reason`, `client_order_id`, `broker_order_id` (у встроенного счёта пусто).
- Продажи (`close`, `stop_fill`, `liquidate`): `entry_price`; `close` и `liquidate`: `fraction` (1.0 у ликвидации и полного закрытия).
- `raise_stop`: котировка в момент подъёма в `price` (пусто, если годной нет).
- `reject`: `action` (`buy`, `close` или `raise_stop`), код в `reason` (коды клетки, `no_price`, `broker_rejected`, `bad_request`, `run_not_active`, `market_closed`), текст в `detail`.
- Только счёт Alpaca: `stop_placed` у `buy` и `close` (`false`, если стоп после сделки поставить не вышло); `recovered: true` у события, восстановленного сверкой.
- Причины `stop_fill`: `stop`, `gap_below_stop`; причины `liquidate`: `liquidate`, `no_quote_entry_price`.

## Поля записи сессии

`day`, `status`, `started_at`, `finished_at`, `stop` (исход цикла), `turns`, `cost` (с аналитиком), `usage` (`input`, `output`, `cache_read`, `cache_write`, `searches`), `model_used`, `fallback_used`, `snapshot_symbols` (сколько цен в снимке, 0 при сбое снимка), `buys`, `sells`, `rejects`, `journal`, `errors`, `analyst` (пусто у участников без аналитика; иначе `cost`, `searches`, `briefing`, `usage`, `model`, `calls` с записью на каждый вызов: `kind`, `question`, `stop`, `cost`, `transcript`) и `transcript`. Пропущенный день пишется без итогов; зависшая сессия получает `stop: "stale"` и ошибку.

## Поля строки `ticks.jsonl`

`ts` (время рынка), `day`, `action`, `equity`, `floor`, `hp`, `stops_placed`, `stop_fills`, `unpriced`, `error`, а у сессии ещё `status` и `cost`. Поля, до которых тик не дошёл (например, ошибка до проверки HP), пустые. Ненормальное число пишется как null, а не роняет запись. Если каталог прогона не пишется, строка пропадает, а результат тика всё равно печатается.

## Значения

- Вид события в журнале: `buy`, `close`, `raise_stop`, `stop_fill`, `liquidate`, `reject`.
- Статус сессии: `started`, `ok`, `cap`, `failed`, `missed`. Сессия, которая «started» дольше 30 минут, считается зависшей.
- Статус прогона: `active`, `finishing`, `finished`, `dead`, `invalid`. Планировщик берёт каждый прогон, кроме `dead` и `finished`. У прогона `invalid` (контрольная сумма конфига не сошлась) отключаются только сессии агента, а проверка HP и стопы работают ([[hp-floor]]).

## Защита от сбоя

- Оборванная последняя строка журнала при чтении пропускается, следующая запись начинается с новой строки, номера `seq` продолжаются.
- Каждая запись журнала сбрасывается на диск сразу. Остальные JSON-файлы пишутся через временный файл и подмену, половина файла не остаётся.
- Сессия за день стартует только один раз: повторный старт получает отказ. Запись создаётся атомарно и эксклюзивно (из двух одновременных стартов выигрывает один), а повреждённый или пустой файл сессии читается как зависший старт со временем изменения файла, поэтому такой день попадёт в «зависшие» и не пропадёт.
- Строки журналов режутся только по символу новой строки, поэтому тезис с необычными разделителями строк не рвёт запись.
- NaN и бесконечность не записываются ни в журнал, ни в JSON-файлы: такая запись даёт ошибку до того, как файл изменится (исключение `ticks.jsonl`: там они становятся null). Одно нечисловое значение в журнале навсегда ломало бы проверку HP.
- Повтором заявки считается только событие `buy` или `close` с тем же `client_order_id`; отказ или стоп с этим id сделкой не считаются, пустой id не совпадает ни с чем.
- Прогон с нечитаемым `state.json` (или с JSON, который не объект) планировщик считает активным, чтобы тик сообщил об ошибке по нему одному.
- Факты сессии для клетки ([[cage-rules]]: покупок за сессию, закрытые сегодня, прогнозы по панели) не хранятся, а считаются из журнала и прогнозов.
